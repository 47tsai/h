# 技術決策紀錄

> 狀態：待確認。本文集中整理技術選擇、建議方案、取捨與尚未定案的問題。建議不等於已決定；正式採用後應更新決策狀態與日期。

## 決策狀態定義

- **待決定**：尚未選定方案。
- **建議方案**：目前最符合需求的方向，但仍需確認。
- **已決定**：已確認並應作為實作依據。
- **延後**：第一版先不做，日後依需求重新評估。

## TD-001：前端框架與語言

- 狀態：建議方案
- 候選：Astro + Svelte + TypeScript
- 建議：沿用既定方向，除非 Phase 0 發現部署或互動需求有重大限制。

### 原因

- Astro 適合以頁面為主、只有部分區域需要互動的網站。
- Svelte 可用於轉換器、碼錶、歷史列表與設定等互動區域。
- TypeScript 有助於約束來源介面、資料模型與同步 API 契約。

### 實作注意

- 不要將所有頁面無條件改成大型單頁應用。
- 業務邏輯應與 Svelte 元件分離，以便獨立測試。
- 選定實際版本前，確認 Astro、Svelte、Tailwind CSS 的相容性。

## TD-002：CSS 與設計系統

- 狀態：建議方案
- 候選：Tailwind CSS，搭配少量共用 CSS 與設計 Token
- 建議：以 Tailwind 建立版面和元件樣式，以 CSS 變數管理主題色彩、字級與間距。

### 原因

- 可維持元件樣式的一致性。
- light、dark、system 主題可共用同一組設計 Token。
- 響應式規則較容易在元件中檢查。

### 不採用的做法

- 不把大量重複的任意值散落在每個元件。
- 不為了視覺效果而犧牲鍵盤操作、對比度或手機可用性。

## TD-003：本機資料庫

- 狀態：建議方案
- 候選：瀏覽器原生 IndexedDB，或在其上使用輕量包裝函式庫
- 建議：以 IndexedDB 作為歷史紀錄、收藏、碼錶紀錄與同步中繼資料的主要本機儲存。

### 原因

- 適合保存多筆結構化資料。
- 不需要使用者登入，也不依賴伺服器。
- 可支援離線使用及本機優先架構。

### 尚待決定

- 使用原生 IndexedDB，或選擇經維護且體積合理的封裝函式庫。
- schema migration 的版本管理與失敗復原方式。
- 匯出檔案格式與匯入時的衝突處理方式。

### 約束

- localStorage 僅適合少量偏好或非關鍵資料，不應當作主要紀錄資料庫。
- IndexedDB 寫入失敗時，UI 不得顯示資料已成功保存。
- 資料模型需有 schema 版本，避免未來更新造成舊資料無法讀取。

## TD-004：狀態管理

- 狀態：建議方案
- 建議：先使用 Svelte 元件狀態與明確的資料服務模組，不預先引入大型全域狀態管理套件。

### 原因

- 第一版的主要資料由 IndexedDB 持久化。
- 元件狀態只負責當前互動、載入狀態與表單內容。
- 集中資料存取層可避免各頁面自行操作資料庫。

若日後出現大量跨頁共享的暫態狀態，再依實際需求評估額外方案。

## TD-005：部署平台

- 狀態：待確認；已有建議方案
- 候選：Cloudflare Workers 統一提供 Astro 靜態資產與同步 API，或 GitHub Pages + 獨立 Cloudflare Worker。

### GitHub Pages + 獨立 Worker

優點：
- Astro 官方提供 GitHub Actions 部署流程。
- 前端靜態託管與同步 API 分離，部署責任清楚。

限制：
- 前端與 API 需分別設定部署、網域與跨來源存取。
- 需留意 Astro 的 site/base 設定及子路徑。

### Cloudflare Workers

優點：
- 可將靜態資產與 API 放在同一個平台管理。
- 有機會讓前端與同步 API 使用同一個 Origin，降低 CORS 設定複雜度。
- Astro 官方目前的 Cloudflare 部署指南指出，Cloudflare 對新專案建議使用 Workers。

限制：
- 需先驗證 Astro 輸出、靜態資產路由與 /api/sync 路由可正常共存。
- 初次部署設定可能比純靜態 GitHub Pages 多一些平台設定。

### 建議

優先驗證 Cloudflare Workers 統一部署，但尚未標記為已決定。先完成最小 Astro 建置、靜態頁面與 API 路由驗證；若不順利，再評估 Cloudflare Pages + 獨立 Worker。

詳細比較與官方參考見 [PHASE_0_DECISION_MATRIX.md](PHASE_0_DECISION_MATRIX.md)。

## TD-006：Cloudflare Worker 與 GitHub 同步

- 狀態：建議方案，安全細節待決定
- 建議：前端只在使用者主動操作時呼叫 Worker；Worker 固定操作單一私人 GitHub 儲存庫及固定檔案。

### 必須遵守

- GitHub Token 僅存放在 Worker Secrets。
- 前端不保存 GitHub Token，也不把它送回瀏覽器。
- 不提供任意 GitHub API 代理。
- 以 GitHub 檔案 SHA 或等效版本資訊處理並行更新。
- 只有伺服器確認寫入成功後才顯示同步成功。
- Worker 無法連線時，本機功能仍可正常使用。

### 尚待決定

- 專用密碼使用伺服器端慢速密碼雜湊驗證，還是成功驗證後換發短效工作階段 Token。
- 限流使用哪種 Cloudflare 能力與持久化方式。
- 第一版同步採單一 JSON 文件，或按資料類型拆分文件。
- 衝突無法自動合併時的 UI 呈現方式。

## TD-007：同步資料格式

- 狀態：建議方案
- 建議：使用具 schemaVersion 的 JSON 文件，資料模型依 DATA_MODEL_AND_MERGE.md 為準。

### 原因

- 方便透過 GitHub Contents API 儲存。
- 容易匯出、備份與人工檢查。
- 適合第一版資料量不大的個人使用情境。

### 風險與限制

- 單一文件會隨紀錄增加而變大。
- 每次更新可能涉及整份文件的讀取、合併與寫回。
- 若資料量或同步衝突顯著增加，應重新評估拆分文件或其他儲存方案。

## TD-008：來源轉換器架構

- 狀態：建議方案
- 建議：採用 SourceAdapter 介面與集中註冊表，各來源獨立實作並測試。

### 介面應涵蓋

- 來源識別與顯示名稱。
- URL 或 ID 輸入解析。
- 輸入格式驗證。
- URL 產生規則。
- 錯誤狀態與可理解的錯誤訊息。
- 必要時提供來源能力資訊，例如是否支援預覽。

### 約束

- 不以大量巢狀 if/else 作為長期擴充架構。
- 未確認的來源規則不應假裝支援。
- 來源清單必須經過逐項確認，並遵守相關服務條款與適用內容限制。

## TD-009：測試策略

- 狀態：建議方案
- 建議：單元測試負責純邏輯，元件測試或整合測試負責 UI 行為，Playwright 負責關鍵端到端流程。

### 最低範圍

- 來源識別、輸入驗證與 URL 產生。
- IndexedDB CRUD 與 schema migration。
- 碼錶經過時間計算及重新載入恢復。
- 同步合併、刪除標記與 SHA 衝突。
- 手機導覽、主題切換、歷史搜尋與收藏操作。
- 網路中斷、GitHub API 錯誤與 Worker 驗證失敗。

測試工具與版本應在 Phase 0 根據實際框架相容性確認。

## TD-010：PWA 與離線能力

- 狀態：延後決定
- 建議：先確保網站的本機資料與核心操作能在離線或同步服務不可用時工作，再評估是否加入 PWA。

### 若納入 PWA，需另行定義

- 安裝體驗與 manifest。
- Service Worker 快取策略。
- 新版本更新提示。
- 哪些頁面資源可快取。
- 如何避免快取過期程式或意外保存敏感回應。

第一版不應為了追求 PWA 標籤而加入難以維護的快取複雜度。

## TD-011：前端資料匯入與匯出

- 狀態：待決定
- 建議：在雲端同步完成前，至少評估提供本機 JSON 匯出與經驗證的 JSON 匯入。

### 原因

- 本機資料是核心資產，不應只依賴單一瀏覽器資料庫。
- 匯出可作為使用者可控的備份與遷移方式。
- 匯入需具備 schema 驗證與預覽，避免錯誤檔案破壞現有資料。

尚待確認是否納入第一版，以及匯入預設採合併還是由使用者選擇合併方式。

## TD-012：第一批來源清單

- 狀態：待決定
- 建議：先列出候選來源並逐一驗證，不在技術決策文件中假設任何尚未確認的來源已支援。

每個候選來源需記錄：

- 名稱與正式網域。
- 支援的輸入類型。
- URL 組成規則及可靠依據。
- 是否需要登入或額外請求。
- 是否可能失效及如何顯示錯誤。
- 服務條款、隱私與內容範圍檢查。
- 對應的單元測試案例。

## TD-013：日期與時區

- 狀態：建議方案
- 建議：持久化時間使用標準化 ISO 8601 時間戳，呈現與每日統計則使用明確設定的使用者時區規則。

### 特別注意

- 碼錶經過時間應以時間戳差值為基礎，而非以畫面更新次數計算。
- 每日統計需明確定義日界線，避免裝置時區變更造成統計跳動。
- 若偵測到系統時間不合理變動，應保留原始時間資訊並採取明確處理策略。

## TD-014：第一版功能邊界

- 狀態：建議方案
- 第一版核心：轉換器、歷史紀錄、收藏、純碼錶、設定、本機持久化。
- 同步：在核心資料層穩定後再加入。
- PWA、複雜來源預覽、標籤分類及進階統計：依 Phase 0 結果決定是否延後。

碼錶不包含倒數、番茄鐘或任務分類。
